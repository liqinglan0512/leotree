# RC1 data safety protocol

The product schema remains version 3. The RC1 persistence envelope has `formatVersion: 1` and a monotonically increasing revision for ordinary commits at `leo-tree-workspace-v1`. Existing v3/v2 keys are read without mutation. A failed read stops fallback, preserves raw source and requires recovery confirmation.

Components submit named operations through `WorkspaceService.bind(renderedWorkspace)`. The operation carries explicit tree identity, base revision, target field preconditions and stable newly created records. Search, filters, focus, selected tree, tabs and dialogs update view state only. No component can submit an arbitrary workspace snapshot. Text operations accumulate in memory for 300 ms and commit in one batch. Navigation does not discard the draft; pending edits cause a browser leave warning.

Every persisted mutation holds the origin-wide Web Lock `leo-tree-domain-write-v1`, reads current storage, validates operation preconditions against that current content and checks the source again before writing. Different fields can rebase safely; incompatible target changes return CONFLICT and retain the local draft. Storage events and BroadcastChannel refresh idle peers. Browsers lacking Web Locks get a degraded state and rescue controls rather than unsafe concurrent writes.

The active domain is made visible by one localStorage `setItem`. Before it, new immutable attachment IDs and bytes finish a single IndexedDB transaction. Failed domain writes remove staged bytes where possible while retaining the original bytes in memory. After visibility changes, no UI or cleanup failure rolls back committed bytes. Successful writes retain one validated last-good workspace; garbage collection protects attachments referenced by the active workspace, last-good candidate, retained legacy community snapshots/covers and pending local drafts. A deleted file can therefore remain for one recovery checkpoint, then be collected when unreferenced. An unreadable reference source defers collection and exposes DEGRADED.

Tree copies allocate new tree IDs and new attachment IDs and copy bytes. Node IDs remain local to their tree. Copies never depend on another tree's attachment ownership. Cancelling a cover selection writes no bytes. Deletion removes descendant and relationship references and normalizes sibling order.

Import defaults to new independent trees. Restore requires an explicit choice of incoming content. Merge retains current conflicting content by default; adopting incoming collisions, including older content, requires a visible choice. The pipeline parses, validates schema and relationships, reports conflicts, builds a preview, then commits atomically. Both revision and reviewed domain content must still match. A graph created by merging otherwise valid inputs is validated again. Missing JSON attachment bytes must be supplied from the local store or explicitly omitted; JSON is never represented as a full backup.

`LeoTree-backup.zip` includes `manifest.json`, `workspace.json`, attachment bytes and retained garden artifacts when present. The manifest records backup/app versions, creation time, knowledge counts, artifact and attachment counts, workspace SHA-256 and each artifact's byte length/hash. `artifactCount` counts manifest-listed payload files (the manifest itself is additional). ZIP import checks paths, declared expansion limits, schema, all required references, counts and hashes before a confirmation can activate it. Existing file IDs are remapped on restore to avoid overwriting bytes; restoring into empty storage preserves original metadata IDs and byte hashes. Retained garden JSON is included in the active domain envelope for atomic activation rather than a second uncoordinated localStorage write.

Recovery first validates a candidate in memory. Confirmation preserves the exact failed raw string in a separate recovery record, verifies that copy, then activates the candidate. Failure to preserve the only raw source blocks activation. The loading overlay is dismissed independently of authentication so recovery controls remain reachable.

SAVE_FAILED never reports a successful save. Pending operations and prepared bytes remain in memory for retry or rescue export. Exporting a draft does not claim it is committed. Storage read errors, malformed JSON, unsupported versions, schema errors and relationship errors remain distinct. A JSON rescue retains readable knowledge content; a complete ZIP requires all referenced bytes to be available.

Evidence and gate status are recorded in RELEASE_STATUS.md and release-evidence. This document describes the implementation; it does not by itself constitute a PASS.
